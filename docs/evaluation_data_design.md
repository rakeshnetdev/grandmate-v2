# Evaluation Data Design

What test data the evaluation harnesses use, how each set is built, and what it can and
cannot prove. The measured results live in [`evaluation_report.md`](evaluation_report.md),
which is generated from recorded runs; the thresholds and gating policy live in
[`../final_docs/v2/evaluation-strategy.md`](../final_docs/v2/evaluation-strategy.md).

This document is about the *inputs*. It exists because a metric is only as trustworthy as
the dataset behind it, and that is the part a results table never shows.

---

## The rule that everything else follows from

**Ground truth never comes from the code being graded.**

A retrieval query whose "correct" chunk was chosen by the retriever, or a move label
produced by the classifier being scored, measures self-consistency and reports it as
accuracy. That failure is silent — it produces excellent numbers — which is exactly why it
has to be designed out rather than watched for.

Two corollaries, both enforced in the harnesses rather than documented and hoped for:

1. **A metric that could not be measured is reported as *not measured*.** It never defaults
   to a passing value. `report.py` renders `None` as "not measured", never as `0.0` or as a
   blank that reads like a pass.
2. **A synthetic set never silently becomes the golden set.** Synthetic data is written to
   `evals/datasets/synthetic/`, never to `golden/`, and no harness reads a synthetic set as
   though it were human-reviewed.

## The datasets

| Dataset | Rows | How it is built | Ground truth comes from | Used for |
|---|---|---|---|---|
| `golden/retrieval.jsonl` | 41 | Derived from the corpus itself: 17 **lexical** (heading verbatim), 19 **semantic** (a paraphrase with the heading name deliberately removed), 5 **negative** (out-of-corpus). Bucket spread: tactics 10, openings 10, strategy 10, rules 6. | **Construction.** Each query's correct chunk is known because the query was generated *from* that chunk. | Dense vs sparse vs hybrid comparison — context precision, recall, MRR |
| `golden/persona_fidelity.jsonl` | 30 | Hand-authored game scenarios, each a set of headers plus deterministic analysis facts, rendered across all three personas. | **The fact set itself.** The test is whether every persona's output preserves it. | `fact_invariance_rate`, `kid_safety_rate`, `grounded_rate` |
| `golden/single_game_chat.jsonl` | 32 | Hand-authored questions over seeded games with known moves, evaluations, and openings. | **The seeded game record** in the database. | Faithfulness, response relevancy, grounding, intent validity |
| `golden/memory_retention.jsonl` | 30 | Hand-authored `(question, answer)` turns with an expected memory kind and expected content — including deliberate negatives that must produce no write. | **The scenario's own label**, written before any model ran. | Retention true-positive and true-negative rates |
| `golden/training_fidelity.jsonl` | 30 | Hand-authored fact sets with a known top weakness. | **The deterministic weakness ranking**, not a model's opinion of it. | `top_weakness_invariance_rate`, `kid_safety_rate` |
| `synthetic/single_game_chat.jsonl` | 68 | Generated by `evals/harness/synthetic_generator.py` — samples real analysed games, generates a question per intent category, derives reference facts from `domain.reports.facts.extract_facts`, tags provenance. | **`extract_facts`** — the same deterministic extraction the production reports use. No LLM writes a reference answer. | Expanding chat coverage beyond the hand-authored set |
| `synthetic/agent_trajectory.jsonl` | 12 | Seeded games with expected routing labels (`expected_needs_retrieval`, `expected_needs_analysis`). | **The scenario labels**, set when the scenario was written. | Single-agent vs multi-agent head-to-head; supervisor routing accuracy |
| *Classifier oracle* (in-harness) | 24 positions | Positions drawn from real analysed games, then labelled by an **independent Stockfish run at depth 24**. | **A deeper, separate engine run** — the production classifier runs at depth 12 with its own thresholds and never sees the oracle. | Detection F1, precision, recall, severity accuracy, per-class breakdown |

## How the layers differ, and why they are separated

**Deterministic layer** — free, reproducible, runs without an API key. The classifier
oracle and the retrieval query set both live here. Scores reproduce exactly for a fixed
dataset, so a change in the number means a change in the system, not noise.

**Judged layer** — costs real money, varies run to run. Faithfulness, response relevancy,
and tone fidelity are LLM-judge scores. They are informative and directionally useful; they
are not exact, and the report says so rather than presenting three decimal places as
precision.

**Structural layer** — not measured at all, in the statistical sense. `grounded_rate`,
`intent_valid_rate`, `staleness_resolved`, and `cross_profile_isolated` are properties the
code *guarantees*: the retry-then-fallback loop makes an ungrounded delivery impossible,
the intent classifier always falls back to a valid taxonomy member, and profile isolation
is enforced at the retriever interface with a `NOT NULL` column behind it. When these read
100%, that is a structural claim verified against real Postgres — not a judge's estimate,
and it should be read differently from a 100% that came from sampling.

Conflating these three is how an evaluation section becomes a rubber stamp. The generated
report marks each metric's kind in its Gate column for exactly this reason.

## The negative control

The classifier harness carries a deliberate self-sabotage: the same evaluation is re-run
against corrupted classification thresholds, and the result is recorded alongside the real
score.

| | Real | Corrupted |
|---|---|---|
| Detection F1 | 1.000 | 0.500 |
| Severity accuracy | 0.750 | 0.125 |

*(Figures from the recorded run — see [`evaluation_report.md`](evaluation_report.md).)*

**A test that cannot fail proves nothing.** The collapse under corruption is the evidence
that the passing score means something; without it, a perfect F1 is equally consistent with
a harness that always returns 1.0. This is the single practice most worth carrying forward
into any new suite.

## Honest limitations

These are real and stated here rather than discovered by a reviewer.

**Every golden set is self-authored and unreviewed.** `reviewed_by` is `null` on every row
of every file. Per the golden-versus-synthetic rule, that makes every judged score
*informative rather than gating* — and the harnesses enforce this by skipping the
reviewed-set-gated assertions rather than quietly passing them. Closing this needs a human
to spot-check samples; it is the single highest-value unblocked action in the evaluation
programme.

**Sample sizes are small.** 24 classifier positions, 12 trajectory scenarios, 3 to 30
scenarios per judged suite. Adequate to catch a regression that breaks a class of
behaviour; inadequate to distinguish a 3-point difference between two systems. The
trajectory run is explicitly flagged `directional_only` in its own record for this reason.

**Retrieval queries retain vocabulary overlap with their source chunks.** Even the
"semantic" queries were written by someone looking at the chunk, with the heading name
removed but the surrounding phrasing intact. This structurally favours sparse retrieval and
is the most likely explanation for hybrid not beating BM25 on context precision at this
corpus size. LLM-generated paraphrases would be a fairer test; the sibling project found
exactly this and the finding is inherited here rather than rediscovered.

**Negative queries have no relevance floor to catch them.** With `RETRIEVAL_MIN_SCORE=0.0`,
every retriever returns its `top_k` regardless of relevance, so all five out-of-corpus
queries produce a 100% false-positive rate. That is a measured consequence of a
configuration default, not a retrieval defect — but it means the negatives currently
measure the *absence* of a threshold rather than the quality of the retriever.

**Judged metrics measure one model.** Everything is scored against `gpt-4o-mini`. Results
would differ on a larger model, and no cross-model comparison has been run.

## Where each dataset is exercised

```
backend/evals/
  datasets/golden/       hand-authored, reviewed_by null
  datasets/synthetic/    generated, provenance-tagged, never read as golden
  harness/               one dataset loader + one eval runner per suite
    synthetic_generator.py   the generation pipeline
  suites/                pytest wrappers — `uv run pytest evals/`
  runs/                  one JSON record per run, timestamped
  report.py              renders runs/ into docs/evaluation_report.md
```

Run everything:

```bash
cd backend
uv run pytest -q                       # 785 hermetic tests, no API key
uv run python -m scripts.ingest_corpus # needs OPENAI_API_KEY
uv run pytest -q evals/                # the evaluation suites
uv run python -m evals.report          # regenerate the report
```
